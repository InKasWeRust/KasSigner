# Reproducible release builds

KasSigner v2.0.0 pins every material build input and builds signed and unsigned
artifacts separately. An unsigned production image is for reproducibility only:
it has no valid developer signature and intentionally halts during boot.

## Public build interface

Use the repository Make facade:

```bash
make release
```

The target performs the pinned host prefetch, immutable toolchain-image construction, network-disabled Docker build, artifact export, and manifest verification through the platform implementation helpers. It does **not** require external audit/HIL/signing-custody attestations merely to reproduce the artifacts. The base is pinned by Ubuntu content digest. System packages are pinned by exact
version, host Rust is 1.87.0, espup is 0.16.0, and Xtensa Rust is explicitly
1.95.0.0. A missing pinned package must fail the build rather than silently
substitute a newer compiler or library.

Before publishing a production release, run the separate fail-closed evidence gate after the artifacts exist:

```bash
make release-readiness
```

That command requires the operator-controlled evidence bindings documented in [`qa/release/README.md`](../../qa/release/README.md).

## Build unsigned verification images

```bash
make release
```

This produces six images: app-only and full-flash for Waveshare,
Waveshare-AF, and M5Stack. Compare unsigned with published unsigned hashes.
Never compare a local unsigned image with a signed release image.

## Build the complete signed and unsigned set

```bash
make release SIGNING_KEY=/path/to/dev_signing_key.bin
```

Optional public parameters are `RELEASE_DIR=/path/to/output` and `REFRESH_INPUTS=1`. The signing key remains an input to the internal Docker secret path; Make does not embed it in the image.

The complete release set contains twelve images:

- `kassigner-waveshare{,-full}.bin`
- `kassigner-waveshare-unsigned{,-full}.bin`
- `kassigner-waveshare-af{,-full}.bin`
- `kassigner-waveshare-af-unsigned{,-full}.bin`
- `kassigner-m5stack{,-full}.bin`
- `kassigner-m5stack-unsigned{,-full}.bin`

It also exports `kassigner-m5stack-partitions.csv`. The release manifest binds
that CoreS3 table by SHA-256 and records its 2 MiB factory-app geometry plus the
final 16 KiB persistent-state reservation. Other hardware targets keep their
own board profile and are not forced to reuse the CoreS3 layout.

## Five-pass convergence

Each configuration builds and hashes five times. Generated hash/signature bytes
are fixed-size `static` objects in flash `.rodata`, and firmware loads them through
volatile reads so LLVM cannot materialize those generated bytes into the executable
segment being hashed. The build therefore requires **passes 2 through 5** to produce
the same executable code-segment hash. One final build is then made from the
converged `firmware_hash.rs`. This makes convergence a determinism assertion rather
than a cryptographic fixed-point search, and prevents shipping a binary whose
embedded hash does not describe its own code segment.

The final ESP application image is then parsed independently of `gen-hash` and
must match the generated code-segment **address, byte length, and SHA-256**.
Ambiguous images containing more than one flash-mapped code segment are rejected.
The physical HIL path uses the same convergence step and, unlike an ordinary
development boot, fails closed if the running mapped segment does not match the
embedded hash. This binds the build artifact to the code bytes actually executed
by the connected CoreS3 before a HIL PASS marker can be emitted.

Boot cryptographic known-answer tests are included in all release configurations.
`skip-tests` is forbidden together with `production`/`silent`.
