# KasSigner Wallet Integration

KasSigner provides a Rust-first integration library that can also be compiled to WebAssembly. Third-party wallets pair **directly with KasSigner hardware**. KasSee is the reference wallet; it is not a service or dependency that another wallet must talk to.

## Crates and generated WASM packages

| Layer | Rust crate | generated WASM/npm package | Purpose |
|---|---|---|---|
| Low level | `kassigner-protocol` | `@kassigner/protocol` | pairing wire formats, PSKT↔KSPT, QR framing/session decode, response validation/merge, finalization |
| Friendly | `kassigner-sdk` | `@kassigner/sdk` | stateful pairing/QR facade and the normal wallet integration workflow |

The npm packages are generated by `wasm-bindgen`. There is no hand-authored JavaScript SDK implementation.

### One canonical KSPT codec

Compact KSPT v4 has one production wire implementation: `kassigner-protocol::wire::kspt`. Its core is `no_std`/allocation-free with `default-features = false`; it owns the KSPT magic/version/flags, binary field layout, compact script-length encoding, signature records, and `N → I → O → S → C → A → D` trailer grammar.

`offline-signer` adapts decoded records into its fixed-capacity hardware `Transaction` model and retains cryptographic transaction interpretation/signing/anti-klepto mechanics. `signer-firmware-core` owns physical review/seed-entropy authorization and other host-testable device behavior. KasSee and `kassigner-sdk` adapt the same codec into host models. No consumer maintains a second KSPT parser or serializer. The same ownership rule applies to multisig descriptor syntax: `kassigner-protocol::wire::multisig_descriptor` is the single bounded parser for `multi`, `multi_hd`, and `multi_hd45`, while KasSee only adapts the parsed representation.

## The wallet keeps wallet policy

KasSigner deliberately does **not** own coin selection. Your wallet keeps control of:

- UTXO discovery and automatic coin selection;
- manual coin control / selected outpoints;
- fees and fee-bumping policy;
- recipients and output construction;
- change-address allocation;
- consolidation and privacy policy;
- gap-limit/restoration state;
- node/provider selection; and
- broadcast.

The integration boundary is therefore:

```text
wallet constructs PSKT using its own policy
        ↓
kassigner-sdk::prepare(...)
        ↓
show raw QR payload(s) using the wallet's QR renderer
        ↓
KasSigner reviews and signs
        ↓
kassigner-sdk::complete(...)
        ↓
kassigner-sdk::finalize(...)
        ↓
wallet broadcasts using its own provider
```

KasWare, Kaspium, or another wallet can retain its existing coin-selection engine unchanged. The SDK is responsible only for KasSigner-specific protocol details.

## Rust: friendly integration

For a source checkout:

```toml
[dependencies]
kassigner-sdk = { version = "=2.0.0", path = "../../crates/kassigner-sdk" }
```

After `2.0.0` is published to crates.io:

```toml
[dependencies]
kassigner-sdk = "=2.0.0"
```

```rust
use kassigner_sdk::{complete, finalize, prepare, Network};

// `pskt_hex` was constructed by the host wallet using its own exact inputs,
// outputs, fee, and change policy.
let request = prepare(&pskt_hex, Network::Mainnet)?;

for frame in request.qr_frames() {
    // frame.payload is raw binary QR payload. Render it with the wallet's own
    // Android/iOS/web/desktop QR library.
    wallet_ui.show_qr(&frame.payload)?;
}

let signed = complete(&request, &scanned_response_hex)?;
let consensus_json = finalize(&signed)?;
wallet.broadcast(consensus_json)?;
```

The friendly API has no `prepareSend`, `createTransaction`, `sendTx`, or `broadcast` operation.

## Rust: low-level protocol integration

Advanced wallets may use the lower-level crate directly. From a source checkout:

```toml
[dependencies]
kassigner-protocol = { version = "=2.0.0", path = "../../crates/kassigner-protocol" }
```

After `2.0.0` is published to crates.io:

```toml
[dependencies]
kassigner-protocol = "=2.0.0"
```

```rust
use kassigner_protocol::{Network, SigningRequest, SigningResponse};

let request = SigningRequest::from_pskt(&pskt_hex, Network::Mainnet)?;
let response = SigningResponse::decode(&scanned_response_hex)?;
let merged_pskt = response.merge_into(&request.original_pskt_hex, request.network)?;
```

This keeps protocol control available without requiring the wallet developer to implement compact KSPT v4, signature merging, QR session framing, or response binding.

## Strict, future-extensible networks

The Rust API uses a typed `Network`. It is `#[non_exhaustive]`: current variants include Mainnet, Testnet-10/11/12, Devnet, and Simnet, while adding a future Kaspa network does not require a major-version source break for callers that match with a wildcard arm.

```rust
match network {
    Network::Mainnet => use_mainnet_policy(),
    Network::Testnet10 | Network::Testnet11 | Network::Testnet12 => use_test_policy(),
    _ => use_non_mainnet_policy(),
}
```

The WASM boundary parses a string once and rejects unsupported values with the stable `wrongNetwork` error category. Unknown strings never fall back to mainnet.

## Stable error categories

Rust integrations receive `ProtocolError` / `SdkError`, each containing a stable non-exhaustive `kind` plus human-readable `message`. Match the kind, not the diagnostic text. For example:

```rust
match complete(&request, response_hex) {
    Ok(signed) => persist_signed_pskt(signed),
    Err(error) if error.kind() == SdkErrorKind::TransactionMismatch => reject_wrong_transaction(),
    Err(error) => report_kassigner_error(error),
}
```

The WASM bindings expose the same categories as `{ kind, message }` error objects. Existing categories cover malformed requests, wrong networks, transaction mismatch, pairing mismatch/replay, QR/session failures, derivation, encoding/decoding, finalization, unsupported operations, and internal failures.

## Normal descriptor pairing

Normal pairing exports the account-level public descriptor/kpub once. The host can then perform unlimited watch-only derivation and normal historical synchronization.

```rust
let account = signer.pair_normal(account_payload, Network::Mainnet)?;
```

The exported descriptor is public-only; private signing material remains on KasSigner.

## Privacy pairing

Privacy pairing avoids exporting account-level public derivation capability. It is stateless on the signer: the host explicitly requests receive/change ranges.

```rust
let request = signer.create_privacy_pairing_request(
    500, // receive start
    20,  // receive count
    700, // change start
    20,  // change count
)?;
```

Each request contains a wallet-generated 16-byte nonce. The response echoes the nonce/ranges and includes a stable, non-secret account fingerprint. `pair_privacy` validates the response against the pending request and against any account fingerprint already associated with that `KasSigner` instance. A successful response consumes the pending request, so replaying it is rejected unless the application intentionally starts a new pairing request.

Responses return typed addresses:

```rust
pub struct DerivedAddress {
    pub address: String,
    pub branch: AddressBranch,
    pub index: u32,
}
```

The host therefore does not need to infer that `receive_addresses[0]` corresponds to a particular branch/index.

Privacy requests support up to 50 receive and 50 change addresses per request and the full non-hardened `u32` child-index space.

## Attaching derivation metadata

When a privacy-paired address is later spent, the host still chooses the input. The protocol crate owns the proprietary encoding needed by KasSigner:

```rust
use kassigner_sdk::{attach_input_derivation, AddressBranch};

let pskt_hex = attach_input_derivation(
    &pskt_hex,
    input_position,
    AddressBranch::Receive,
    derived_address.index,
)?;
```

The wallet chooses the address and input; the SDK handles KasSigner-specific PSKT metadata. The hardware treats this KSPT v4 derivation value as an **untrusted hint**: it derives that child and verifies the resulting x-only public key against the UTXO script before signing.

`attach_output_derivation` is available for host-owned output metadata when needed.

## QR ownership and concurrent sessions

`QrFrame.payload` is raw binary. The protocol crate never renders SVG or chooses a UI QR library.

Each `KasSigner` and each low-level `QrDecoder` owns its own decoder state. Two integrations can therefore process independent multi-frame sessions without sharing hidden thread-global state.

## Response validation

`complete` does not merely accept a signature blob. It merges the signed KSPT response into the original PSKT while enforcing transaction-bound compatibility. A signed response from another transaction is rejected.

The host wallet remains responsible for broadcasting only after its own final policy checks.

## Deterministic conformance vectors

`docs/integration/vectors/kassigner_sdk_v2.json` locks:

- privacy request bytes;
- nonce/range echoing;
- stable account fingerprint derivation;
- privacy response bytes;
- typed receive/change index mapping;
- raw multi-frame QR session bytes;
- strict accepted/rejected network strings; and
- an exact compact KSPT v4 vector with trailer ordering `N → I → O → S → C → A → D`.

The QA conformance target consumes the same file, so the documentation vector and executable contract cannot drift independently.

## Native versus WASM dependency graphs

Native Rust is the default SDK path. `kassigner-protocol`'s normal `host` feature does not activate `wasm-bindgen`/`js-sys`, and `kassigner-sdk` keeps WASM dependencies behind its explicit `wasm` feature and `wasm32` target. The generated npm packages are built with `--no-default-features --features wasm`. The public standalone build is `make sdk`, which writes `@kassigner/sdk` to `target/sdk/kassigner-sdk/pkg`; it does not build the KasSee application bundle.

## Licensing boundary

The reusable integration dependency graph is permissive: `shared-signer`, `kassigner-protocol`, and `kassigner-sdk` are dual-licensed **MIT OR Apache-2.0**. `shared-signer` is included because it is a transitive dependency of `kassigner-protocol`; leaving it GPL-only would defeat permissive SDK linking. The KasSigner/KasSee product remains GPL-3.0: `signer-firmware-core`, `offline-signer`, `online-watcher`, firmware/apps, GUI/CLI, and the repository's root application license are not relicensed by the SDK exception.

## Distribution verification

First-party Rust versions are pinned at `2.0.0`. Public path dependencies also include `version = "=2.0.0"`, allowing Cargo to normalize those paths to registry dependencies in packaged manifests. The source tree is **publish-ready plumbing**, not evidence that the packages are already present on crates.io or npm; use registry/package-manager installation syntax only after the corresponding `2.0.0` artifacts are actually published.

The crates.io publish order is:

1. `shared-signer` 2.0.0
2. `kassigner-protocol` 2.0.0
3. `kassigner-sdk` 2.0.0

Use the platform distribution checker before publishing:

```bash
scripts/linux/build/sdk-distribution-check.sh
```

or:

```powershell
scripts\windows\build\sdk-distribution-check.ps1
```

Those checks package the three Rust crates, build both generated WASM packages, and run npm package dry-runs. `--registry-dry-run` additionally invokes Cargo registry dry-runs and is intended after each predecessor dependency version is available in the configured registry.

## Security/conformance expectations

The repository E2E suite exercises the friendly SDK through the actual `offline-signer`, including a high derivation index. Negative coverage includes wrong derivation hints, correct index with the wrong UTXO pubkey, a response from a different transaction, pairing nonce/account mismatches, replay handling, strict networks, independent QR decoders, and the maximum 50+50 privacy batch.
